The Weekly Digest: the landing page, mailed

The digest is the This Week landing projected into the most hostile rendering environment in the product: Outlook, often on a phone, images blocked by default, dark mode inverting colors at random. So the digest is typographic only, built like it's 2004 on purpose, and complete without a single click. It is to the landing what the report is to the case file: a projection, never a second source.

01 · Laws of the digest

Inherits everything upstream. Adds six.

D1
The subject line carries the finding.
"Steam attrition · Week of Jul 6 · 3 new Critical · 15 to review." A manager triaging an inbox gets the week's answer without opening the email. Subject format is fixed so a mailbox search for "Steam attrition" returns a readable series.
D2
Complete without clicking.
Recipients may not have dashboard access, and even those who do won't log in from a phone. Every finding, event, and queue entry reads whole in the email body. Links deepen; they never complete.
D3
Built like it's 2004.
Single column, 600px, table-based stacking, inline styles, system fonts only (Arial for prose, Courier New for numbers, the email-safe cousins of Inter and Plex Mono). No images at all: Outlook blocks them by default, so a chart in email is a broken icon. If it needs a chart, it links to the case file.
D4
Color never carries meaning.
Dark-mode clients invert colors unpredictably. Severity is carried by words and weight ("CRITICAL" in bold Courier); the single red accent is an enhancement that can vanish without losing a bit of information. Same principle as the report's grayscale rule (R3), one notch stricter.
D5
Drafted, then owned.
The digest is composed from the same events.json the landing renders, then the analyst edits before it sends. Never auto-sent. Same principle as the report signature (R5): the model drafts, a person owns. The compose flow lives behind the landing's orange button.
D6
A plain-text twin always ships.
Every digest generates a text/plain alternative with identical content. This is both email hygiene and the escape hatch if ConEd's answer to the open format question turns out to be "plain text, please." The twin costs nothing because the HTML is already typographic.

1

Subject and kicker

Finding in the subject (D1), vintage in the kicker (W1 survives the medium: "data through run Jul 6," never "just now"). The series format makes six months of digests a searchable record of the program.

2

Finding paragraph

The queue arithmetic from the landing (W4), written as prose because email is a reading medium. The Critical definition is restated inline in parentheses, since this reader may never see the methodology page. Written in the recap style the project already uses: specific, output-oriented, no filler.

3

Queue items

Two lines each: identity and claim in Arial, evidence and link in Courier. The severity word is bold Courier, legible after any dark-mode inversion (D4). Only the top three ship; the digest is a briefing, not an export.

4

Events in prose

The same event grammar (W2), compressed. Aggregates stay aggregated: the vintage drop is one sentence here just as it was one line on the landing.

5

Method footer

The honest-framing block travels with every artifact that leaves the tool (R4 applied to email). The AUC translation appears in the same words used on the case file and report, because consistency of the caveat is what makes it credible rather than boilerplate.

03 · The compose flow

Behind the orange button

C1
Draft.
"Compose weekly digest" assembles the draft from events.json and the queue state: subject, finding, top three, events, pulse, footer. Generation is deterministic templating plus one LLM pass for the finding paragraph, with every number injected from data, never generated.
C2
Edit.
The draft opens in an editable view on the workbench. The analyst can reorder queue items, cut events, and rewrite prose. Injected numbers render as locked tokens; editing around them is free, editing them requires deliberately unlocking, which keeps the digest a projection (D5 meets R1).
C3
Send, minimally.
V1 sends nothing: it opens the draft in the analyst's own Outlook via mailto (plain-text twin) or copies rich HTML to the clipboard. This dodges SMTP integration, deliverability, and the territory-gating question entirely, and it means the email always genuinely comes from the analyst. Direct send is a later increment if ConEd asks.
04 · Open questions before this ships
  • Format preference, still open with David. This spec's answer to "plain text or HTML" is "both, always" (D6), which makes the question low-stakes. But cadence (weekly? aligned to pipeline runs?) and the recipient list are genuinely his to answer, and they're already on the client-notes question list.
  • The finding paragraph's LLM pass. One generated paragraph per week, numbers injected not generated, analyst-edited before send. Decide whether it routes through the existing /api/query infrastructure or a dedicated prompt, and pin the template so tone doesn't drift week to week.
  • Locked-token editing. C2's locked numbers need a small editor behavior (contenteditable with token spans, or a structured form per section). Worth a spike before promising; the fallback is a plain textarea and trust, which is honest for a single-analyst v1.
  • Link durability. Case-file and report links in a digest outlive container redeploys only if BBL-keyed routes are stable and reports persist (Spec 3's storage question). Emails are forever; make the URLs deserve it.
